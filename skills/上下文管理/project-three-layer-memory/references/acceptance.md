# 项目接续验收

本页描述怎样验证，不代表某个安装环境已经全部通过。记录实际命令、文件位置和结果，区分以下三种证据。

Codex 首版的 54 项脚本测试见 [首版发布 PR #24](https://github.com/xiangruiai/xiangrui-toolkit/pull/24)；两次独立 Codex 原生运行另有交付验收记录，不能仅从该 PR 的脚本结果推定。这些都是该版本、该宿主的既有证据。多宿主改造要另做受影响回归；Claude Code、Gemini CLI、Cursor 的配置文件检查不能冒充各自已登录原生会话的接续验收。

## 1. 脚本行为

使用临时项目和隔离的用户/宿主配置目录，避免修改真实工作资料。建议覆盖：

| 场景 | 应观察到的结果 |
|---|---|
| 无 Git 的普通项目 | 能在明确指定的项目根初始化与读回 |
| 预览 | 输出改动计划，目标文件不变 |
| 重复初始化或同内容安装 | 不重复追加协议，不覆盖已有正文 |
| 现有项目入口 | 能映射已读过的背景、方法、状态文件，保留原文 |
| 存在有效 override | 接入实际生效的规则入口，其他规则保留 |
| 自定义 `CODEX_HOME` | 全局协议位于实际指定目录 |
| 默认 generic | 不误写 Codex 配置，未接入的规则文本明确待处理 |
| Claude/Gemini 项目桥 | 保留已有原生入口，桥共存并引用同一项目权威规则 |
| `CLAUDE_CONFIG_DIR` 与 `GEMINI_CLI_HOME` | 配置目录与用户替代根按各自语义处理 |
| Gemini 自定义 `context.fileName` | 核对真实全局入口，不凭默认桥宣称已加载 |
| Cursor 全局请求 | 生成待粘贴文本，返回手动动作与未启用状态 |
| generic 显式全局文件 | 只追加受管块，保留宿主加载尚未验证的说明 |
| 两个独立项目 | 记录与召回各自有界，互不混入 |
| 状态被并发修改 | 旧 SHA256 的 checkpoint 被拒绝，原件保留 |
| 缺来源、危险路径或疑似秘密 | 明确失败，避免写入不可信或敏感内容 |
| 项目退出标记 | 不自动初始化或写入该机制 |
| 撤销原生文件全局默认 | 只移除本包受管全局块，保留其他规则与项目文件 |
| Cursor/generic 手动模式退出 | 返回界面移除说明，不伪装已关闭 User Rules |

还应检查命令失败是否返回明确错误，以及 `audit` 是否保持只读。结构校验只能说明包和命令格式，不能证明模型会选择 Skill、读取项目或继续实际工作。

## 2. 两次独立模型运行

在模型已配置且允许执行工具的环境中，用一个明确的临时项目验证。使用两个独立 run，第二次不传第一段完整聊天记录。

**第一次运行：**

1. 显式选择真实宿主安装 Skill 并接入隔离的全局规则，确认实际入口与安装路径。手动模式需先在宿主完成接入，不能跳过。
2. 给出一个小而真实的项目任务、明确约束和一个有用的后续步骤。例如整理一份调研材料：先完成来源清单，下一次再作比较。
3. 让 Agent 完成第一步，保存真实结果、来源和当前交接。检查它实际写出的文件，不接受“已经记住”作为唯一证据。

**第二次运行：**

1. 从同一项目根启动，只说：“继续这个项目，先读回目标、上次结果和未完事项，指出来源，再完成下一步。”
2. 检查模型是否实际调用文件工具或 `resume`，准确引用该项目文件。
3. 检查它能否分清已完成与待办，遵守已确认约束，并生成下一步的真实成果。
4. 检查成果和更新后的交接，不将读回成功等同于整个项目完成。

真实模型测试应报告模型、宿主、两次运行、项目目录与证据位置。若账户、额度、网络或工具权限阻塞，保留脚本测试结果并说明未完成的模型验收，不捏造通过记录。

## 3. 各宿主原生新对话

在目标桌面环境另行验证：安装后打开准确项目，完成一次带文件结果的工作，再新建同项目对话继续。确认新对话实际拿到了有效全局规则、项目入口和接续文件。

CLI 独立 run 通过可以证明该 CLI 环境的接续；它不能自动代表桌面旧会话已热加载，或所有桌面版本和账户都已验收。Codex 通过不自动代表 Claude Code、Gemini CLI 或 Cursor 通过。缺少某个宿主验证时明确写“该宿主原生新对话未实测”；缺少桌面验证时写“桌面新对话未实测”。

Claude Code 可核对 `/memory`、`/context` 中的实际来源，Gemini CLI 可核对 `/memory show` 和 `/skills list`，Cursor 可核对 User Rules 与 Agent 实际引用的项目文件。最终仍应看它有没有正确读取、区分事实状态并继续实际任务，不用入口列表代替项目接续。

## 触发边界示例

这些是可供人工或模型评估的场景，不是已执行评测结果：

| 用户请求 | 预期行为 |
|---|---|
| “给这个新课程项目建立三层记忆” | 在明确项目根接入，复用适合的现有文档并识别真实宿主 |
| “继续上次的项目，看看做到哪里” | 读回当前交接，按来源继续未完事项 |
| “这个项目以后交付前先检查来源链接” | 在已有授权与明确依据下记录程序记忆 |
| “查一下当时为什么改范围” | 有界召回相关历史并给出处 |
| “解释一下三层记忆是什么” | 直接解释，不初始化项目 |
| “把这段话压成一句” | 完成改写，不因全局默认生成记忆文件 |
| “以后我喜欢短回答，记住” | 识别为个人偏好，不能写进当前项目画像或擅改个人档案 |
| “只读审阅这份计划” | 只读，不把计划标为已完成或制造阶段进展 |
| “我在 Cursor，安装并启用所有项目默认记忆” | 安装本地 Skill，给出可粘贴 User Rules 和真实待处理动作 |
| “现在换成 Claude Code 继续同一个项目” | 连接原生入口，使用原有项目记忆，验证新宿主加载 |
| “扫描整个 Documents，为每个目录建记忆” | 不以默认接入扩大范围；明确实际项目和授权后再处理 |

## 完成报告

至少写清：实际宿主、安装与全局入口或待接入文本、当前项目映射与原生桥、脚本检查结果、该宿主模型接续结果、桌面是否实测，以及仍影响使用的具体限制。不要用测试数量代替用户真正依赖的接续行为。
